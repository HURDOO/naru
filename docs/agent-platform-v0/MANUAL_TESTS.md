# Agent Platform v0 사용자 Manual Test

자동 인수([ACCEPTANCE.md](ACCEPTANCE.md))로 확인하지 못하는 실제 사용 경험을 사용자가 직접 확인한다. 각
항목에는 준비, 절차, 기대 결과, 보고할 내용을 적었다.

## 0. 준비

두 가지 방법 중 하나를 고른다.

- 로컬 sandbox(배포 없이, 가짜 runtime): 화면과 흐름만 볼 때 쓴다.
  - `pnpm build`(web은 `NARU_APP_BASE_PATH=/`) 뒤 다음을 실행한다.

    ```sh
    node --import tsx tests/spikes/agent-platform/ui-sandbox.ts
    ```

  - 출력된 주소, 비밀번호, project 경로로 접속해 project를 연결한다.
  - 관제실 `무엇을 맡길까요?`에 `@project PLAN …`을 보내면 가짜 메인·프로젝트 오케스트레이터가 작업자
    둘과 리뷰어 하나, 작업 네 개를 만든다. 작업자 하나는 명령 승인을, 하나는 결정을 기다린다.
  - 대화에서 직접 `DEMO`(개발 서버와 직접 확인 부탁), `APPROVE`, `SLOW`를 보낼 수도 있다.
- 실제 instance(배포 후, 실제 모델): 운영 배포는 별도 승인이 필요하다.
  - Agent Platform은 `NARU_AGENT_PLATFORM=1`일 때만 켜진다. 기본값은 꺼짐이다.
  - Claude Agent SDK는 사용자가 설치하고 `NARU_CLAUDE_AGENT_SDK_PATH`로 알려 준다(AP-D012).
  - 처음에는 중요하지 않은 project 하나로 시작한다(AP-T19 pilot).

## 1. 기존 기능이 그대로인지 (A01)

1. Gateway에서 passkey로 로그인한다.
2. 기존 project, 작업공간, Codex·Claude·terminal Pane을 연다. 입력과 재접속을 해 본다.
3. Codex 또는 Claude 작업을 끝까지 돌려 완료·입력 필요 알림(Hook, push)이 오는지 본다.
4. `NARU_AGENT_PLATFORM=0`으로 한 번 더 확인한다. `에이전트` 탭이 보이지 않아야 한다.

- 기대 결과: 이전과 같다. top bar의 `작업공간 | 에이전트` 전환과 "나를 기다림"만 추가로 보인다.
- 보고: 달라진 점, 알림 누락, 재접속 문제

## 2. 전체 목표와 프로젝트 계획 (A02, A03)

1. `에이전트` → `관제실`의 `무엇을 맡길까요?`에 두 project의 목표를 적는다. `@alpha` 같은 칩으로
   project를 언급한다. 메인 오케스트레이터가 없으면 이때 고른 런타임으로 시작된다. 예:
   "@alpha 로그인 화면 정리 / @beta 문서 목차 정리. 계획과 작업만 만들어."
2. 관제실 `작업 흐름`에 project마다 오케스트레이터, 작업, 담당, 연결선이 그려지는지 본다.
3. `흐름`에서 `계획 문서`와 작업 상세(진행 기록, 병합 조건)를 본다.
4. `흐름` → `프로젝트에 지시`로 방향을 바꾼다(예: "passkey만 쓴다").
5. 작업자의 `대화`에서 새 지시가 오케스트레이터 이름이 붙은 요청 말풍선으로 보이고, `원본 지시`가
   내 지시를 가리키는지 본다.

- 기대 결과:
  - 각 project에 오케스트레이터가 하나 생기고, 계획과 작업이 나타난다.
  - 작업 상세의 원본 지시가 사용자 지시와 연결된다.
  - 바뀐 지시가 다음 위임에 인용된다.
- 보고: 계획의 질(사용자 의도와 맞는지), 불필요한 질문, 반복 wakeup

## 3. Claude Chat ↔ TUI (A07)

1. Claude 작업자 대화 → `⋯` → `TUI에서 직접 이어받기` → 작업공간의 Pane에 같은 대화가 열리는지 본다.
2. TUI에서 한 줄 지시한다. 그 말이 대화에 `나 · TUI` 말풍선으로 보이는지 본다.
3. 대화로 돌아와 `오케스트레이터에게 돌려주기` → 대화가 이어지는지 본다.
4. 대화 입력창에 직접 써서 보낸다. "여기부터 내가 직접 대화 중" 줄이 생기고, 에이전트가 답하는지 본다.

- 기대 결과: 대화 기억이 이어진다. 전환 중 실패하면 원래 상태로 돌아간다.
- 보고: 전환 시간, 화면 깜빡임, 대화 누락

## 4. Codex Chat ↔ TUI (A06)

3번과 같다. Codex 작업자로 한다(모델 `gpt-6-astra`).

- 기대 결과: TUI는 사람이 writer일 때만 입력할 수 있다. 오케스트레이터가 writer이면 거부 메시지가
  보인다.

## 5. 개발 서버와 직접 테스트 요청 (A08, A14)

1. 작업자에게 "개발 서버를 start_process로 띄우고 로그인 흐름을 직접 확인해 달라고 요청해"라고 지시한다.
2. 작업자 대화 오른쪽 `띄워 둔 프로세스`에 서버가 보이는지, `열기`로 로그가 보이는지 본다.
3. 관제실 `나를 기다리는 것`의 `직접 확인 부탁` → `확인하기`를 연다. 준비된 환경과 확인 절차가 있는지
   본다. 직접 확인한 뒤 답을 보낸다.

- 기대 결과: 요청에 접속 주소와 절차, 예상 결과가 있다. 결정 뒤 그 작업만 다시 진행된다.
- 보고: 요청 내용이 실제로 테스트 가능한 수준인지

## 6. 비밀번호가 필요한 터미널 (A09)

1. 작업자에게 SSH나 ansible처럼 비밀번호를 묻는 작업을 시킨다(시험용 대상만).
2. 에이전트가 `터미널 입력 부탁`(나를 기다리는 것)을 보내는지 본다. 직접 비밀번호를 치지 않아야 한다.
3. `확인하기` → `넘겨받고 열기` → 터미널 도구 모음의 `비밀 입력`으로 비밀번호를 넣는다.
4. 그 에이전트 대화의 프로세스 `돌려주기` → 에이전트가 화면을 다시 읽고 이어 가는지 본다.

- 기대 결과: 비밀번호가 Naru 기록, 에이전트 대화, 다른 기기의 관찰 화면에 남지 않는다.
- 보고: 에이전트가 넘겨주지 않고 직접 입력하려 했는지, 반환 뒤 이어 가는지

## 7. 병렬 작업 통합 (A11, A15)

1. 프로젝트 오케스트레이터에게 두 작업을 각각 worktree에서 진행하라고 지시한다.
2. `흐름`에서 작업을 눌러 branch 산출물, 리뷰, 병합 조건을 본다.
3. 리뷰가 통과한 뒤 `merge_task`로 통합되는지 본다. 두 작업이 같은 파일을 고쳤다면 충돌로 거부되고,
   작업자가 worktree에서 풀어 다시 리뷰받는지 본다.

- 기대 결과: 작업마다 merge commit이 생긴다(`Merge naru/…: 작업 제목`, 작성자는 사용자 git 신원).
  충돌이 나도 project checkout은 merge 전 그대로다. 의도 리뷰가 실패하면 통합되지 않는다. push는 하지
  않는다.
- 보고: merge commit 방식(AP-D019)이 쓰기 편한지, 바꿀 점

## 8. 도구 승인 (AP-D017)

1. 작업자가 명령을 실행하려 하면 `나를 기다리는 것`과 그 대화 안에 `명령 실행 승인`이 보이는지 본다.
2. Naru를 보지 않는 상태(휴대폰 잠금 등)라면 "입력 필요" 알림이 오는지, 누르면 그 에이전트가 열리는지
   본다.
3. 대화를 넘겨받지 않은 채 승인 또는 거부한다. 기기의 알림이 사라지는지 본다.

- 기대 결과: 에이전트는 내 Claude와 같은 권한 모드(auto)로 일한다. 묻는 것은 그 모드가 결정하지 못한
  것뿐이고, 무엇을 실행하려는지 보인다. `이 세션에서는 항상 허용`을 고르면 같은 종류는 그 세션 동안 다시
  묻지 않는다(AP-D023).
- 보고: 너무 자주 묻는지, 더 미리 허용할 명령이 있는지(project `.claude/settings.json`)

## 9. 휴대폰 (360px)

1. 휴대폰으로 `에이전트`를 연다. 아래 탭(관제실, 대화, 흐름)을 오가고 대화를 열고 닫는다.
2. 결정, 승인, `맡기기`, 공유 프로세스 넘겨받기와 `비밀 입력`을 해 본다.
3. Handoff 알림(push)을 눌러 그 질문이 열리는지 본다.

- 기대 결과: 가로 스크롤이 없다. 키보드와 버튼을 쓸 수 있다. 알림이 해당 항목을 연다.

## 10. 새 화면의 쓰는 느낌 (AP-D022)

1. 대화가 실제 에이전트와 이야기하는 느낌인지 본다: 내 말과 답이 중심이고, 도구 호출은 회색 한 줄로
   접혀 있다가 펼쳐진다.
2. 관제실 한 화면에서 누가 무엇을 맡았고 어디까지 왔는지, 무엇이 나를 기다리는지 바로 보이는지 본다.
3. 오케스트레이션을 어디서 시작하는지 헷갈리지 않는지 본다.

4. 에이전트가 무언가 물으면 대화에 질문 카드(질문, 선택지, 추천)가 보이는지 본다. 대시보드 대신 대화로
   답해 보고, 에이전트가 그 질문을 스스로 거둬 대시보드에서 사라지는지 본다.

- 보고: 어색한 문구, 찾기 어려운 버튼, 너무 많거나 부족한 정보, Figma 시안과 다른 점

## 결과를 돌려줄 때

항목마다 PASS·문제 있음·못 해 봄 중 하나와 짧은 메모를 남긴다. 운영 한도(동시 에이전트 수, 예산,
wakeup 빈도)는 이 결과를 보고 AP-T19에서 함께 정한다(AP-D007).
