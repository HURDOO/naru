# 사람의 개입 원칙 (Human-in-the-loop)

언제 사람에게 묻고 언제 에이전트가 스스로 정하는지의 기준이다. Naru가 관리하는 에이전트와, Naru를
만드는 에이전트 모두에 적용한다. 근거는 SOURCE_SPEC의 INV-01, INV-02, INV-04, INV-06, INV-08과
§9, 그리고 AP-D003, AP-D005, AP-D017, AP-D021, AP-D023이다. 사례가 생기면 아래에 더한다.

## 원칙

1. **사람이 이미 정한 것은 사람의 것이다.** 사람이 쓰는 설정, 모드, 도구, 기본값과 습관을 바꾸거나
   좁히는 판단은 에이전트가 대신 내리지 않는다. 바꿀 이유가 보이면 지금과 바뀐 뒤를 구체적으로 보여
   주고 묻는다.
2. **원칙을 늘려 해석하지 않는다.** "X는 사람이 확인한다"는 X에만 적용한다. 원칙에서 더 강한 규칙을
   끌어내면 그것은 새 결정이다. 새 결정이라고 밝히고 승인을 받는다.
3. **묻는 것은 멈추는 것이 아니다(INV-06).** 막힌 일만 멈추고 나머지는 계속한다. 질문에는 추천, 근거,
   대안, 준비된 환경과 다시 이어 갈 조건을 붙인다(§9.2).
4. **코드로 막는 것은 안전과 되돌릴 수 없는 일뿐이다(INV-02, INV-09).** 비밀, 배포, 파괴적 변경, 외부
   전송, 권한 확대가 그렇다. 나머지는 LLM이 판단하고, 사람의 직관이 필요한 곳에서만 묻는다.
5. **최신 사용자 지시가 이긴다(INV-01, INV-08).** 에이전트의 재해석은 원문을 대신하지 못한다.

## 사례

### 1. 사용자의 auto 모드를 마음대로 엄격하게 바꿈 (2026-10-16)

- 상황: AP-D017에서 "명령 실행은 사람이 확인한다"고 정했다. 구현하면서 이를 "관리형 Claude를 사용자
  자신의 Claude보다 엄격한 권한 모드로 띄운다"로 늘려 해석했다(작업자 `acceptEdits`, 오케스트레이터
  `default`).
- 결과: 사용자는 평소 auto 모드로 쓰는데, Naru 에이전트만 셸 명령마다 승인을 물었다. 사용자는 이를
  예상하지 않았다. INV-04(일반 Bash·파일 도구 실행은 기본적으로 유지)와도 어긋났다.
- 무엇이 틀렸나:
  - 사용자가 이미 고른 모드를 바꾸는 결정을 대신 내렸다(원칙 1).
  - "확인한다"를 "더 엄격한 모드"로 늘려 읽었다(원칙 2).
  - 결정 기록에 "auto를 default로 바꾼다"는 사실이 드러나지 않아 사용자가 검토할 기회가 없었다.
- 바로잡음(AP-D023): 관리형 에이전트는 사용자 자신의 모드로 시작한다. Naru의 승인 요청은 그 모드가
  묻는 것만 받고, 런타임이 제안하면 "이 세션에서는 항상 허용"을 고를 수 있다.
- 에이전트 지침에 넣은 것: 원칙을 사람의 기존 선택을 바꾸는 쪽으로 읽게 되면, 지금과 바뀐 뒤를 보여
  주고 묻는다(`naru-orchestration`의 "Asking a person").
